## Findings

### 1. End-to-end asset-generation workflow (checklist: concept art → provenance)

The prompt.txt checklist enumerates a 17-stage pipeline. Industry sources confirm this shape is how real slot studios structure production, with AI inserted at specific stages rather than end-to-end [S1][S2][S13].

1. **Concept art** — [observed] AI-first concept exploration is the highest-ROI insertion point. One production audit found AI-assisted concept pipelines cut concept-to-greenlight from ~18 days to ~4 days while raising concept variants reviewed per project from 8 to 47 [S2]. Twin Win Games (slot art vendor, Feb 2026) runs two codified pipelines: "AI-enhanced manual" (hero characters, licensed IP; ~20–25% time saving, 4–5 weeks → 3–4 weeks) and "AI-first" (symbols, UI, backgrounds, decorative assets; 3–4 weeks → 2–3 weeks), with a curation rule that clients only ever see 2–3 curated directions, never raw output [S13].
2. **Style bible** — [mandatory per skill contract] authored before any batch generation; see §2.
3. **Symbol design** — [recommended] silhouette-first workflow; see §3.
4. **Background design** — [observed] delivered at full canvas resolution (1920×1080 landscape base; 1080×1920 portrait variant) in far/mid/near layers so the engine can parallax during spins and feature transitions [S3][S4].
5. **Foreground design** — [observed] separate transparent overlay layers (framing foliage, set dressing, vignette) delivered apart from the background so they can sit above reels without occluding symbols [S3][inferred: layer ordering is standard compositing practice, rarely written down explicitly].
6. **Reel-frame design** — [observed] delivered as a layered file with separate masks for backlit areas; payline/win overlays as separate transparent layers the engine toggles per win [S3].
7. **Interface-component design** — [observed] UI is often authored vector-first or at 2× raster and sized for responsive breakpoints; 9-slice used for panels/buttons (see §7.4) [S3][S12].
8. **Feature-environment design** — [inferred from skill contract + observed practice] each tier (`feature`/`super_feature`/`ultimate_feature`) gets a visually escalated environment variant (palette shift, lighting change, added FX layer) rather than a whole new scene, to bound asset cost while satisfying the "materially different presentation" rule (CONVENTIONS §9.3).
9. **Character design** — [observed] hero characters are the one asset class vendors keep in the human-led pipeline; AI cannot yet handle "emotional nuance and character personality" or licensed-IP compliance without human oversight [S13].
10. **VFX design** — [recommended] particles/glows/trails are generated as small grayscale/white alpha elements and tinted in-engine, not baked as colored frames; AI models' tendency to add soft feathered glows makes raw AI output unsuitable for particle textures without a hard-alpha cleanup pass [S6].
11. **Animation-layer separation** — [recommended] symbols and characters are cut into parts (body/limbs/face/props/glow layer) for Spine or cutout rigging; a single flattened AI image must be segmented + inpainted behind parts before rigging (see §6).
12. **Rigging** — see §6 (Spine vs sprite-sheet trade-off).
13. **Texture-atlas generation** — see §7.
14. **Compression** — see §7.3.
15. **Device-profile variants** — [observed] slots ship art at multiple resolutions for desktop/tablet/phone, often as @1x/@0.5x atlas variants; responsive portrait mode may load a separate UI pack [S3][S4].
16. **Manual cleanup** — [mandatory in practice] every vendor source keeps "human paintover as a standard stage"; AI-specific QA checks target anatomy errors, garbled text, tiling artifacts [S2][S13].
17. **Visual QA** — [recommended] QA sprites at 200–400% zoom against both light and dark backdrops to catch halos; verify true alpha programmatically (one dev found only 14 of 120 "transparent" icons had real alpha) [S6].
18. **Provenance recording** — see §8.

### 2. Style bible — required contents and rationale

[mandatory per skill contract] The style bible is the consistency anchor for every downstream prompt. Industry style-guide practice for slots confirms each element the checklist requires [S1][S5]:

- **Original theme / narrative / mood** — the theme statement is what all prompts share verbatim (the "style anchor," §4.1).
- **Shape language** — sharp silhouettes read as danger/magic/intensity; round as friendly/abundant; angular as tech/machinery/strength. Encoding a per-tier shape rule (e.g. premiums = ornate radial shapes, lows = simple glyphs) is standard [S1].
- **Material language** — a fixed material set (e.g. "aged gold, carved jade, weathered wood") repeated in every prompt is one of the strongest consistency levers for diffusion models [S2][observed in studio prompt-library practice].
- **Lighting** — one canonical key-light direction + rim-light color for all symbols so they composite onto one background without looking pasted [inferred: basic compositing requirement, universally practiced].
- **Camera perspective** — symbols: straight-on orthographic-feel, zero perspective distortion; backgrounds: one stated horizon/eye-level [S1][inferred].
- **Color roles** — palette locked as roles, not just swatches: background-dominant, symbol-accent, UI-chrome, win-celebration, per-tier feature accents. Colors chosen so symbols never merge with each other or the background [S1].
- **Contrast rules** — symbols must separate from background at all times; detail density tiered (simpler for low-pays, richer for premiums) [S1].
- **Symbol silhouettes** — "solid black spot" test: every symbol must be identifiable as a pure silhouette [S1] (see §3).
- **Character / environment / UI / VFX rules** — per-class dos-and-don'ts.
- **Typography** — display face for big-win/feature titles + UI face; big-win typography is its own asset class (see prompt list §9 of checklist).
- **Feature / Super Feature / Ultimate Feature visual language** — [mandatory per skill contract] escalating visual identity per tier (e.g. bronze→silver→gold framing, intensifying palette temperature, added FX density) so tiers are "materially different in presentation" (CONVENTIONS §9.3).
- **Prohibited references** — per-game list instantiating the global prohibitions (§9 below).
- **Mobile-readability requirements** — see §3 numbers.
- **Accessibility requirements** — text contrast ≥ 4.5:1, no color-only information, flash ≤ 3/s (mirrors CONVENTIONS §9.7).

### 3. Symbol design rules — silhouette, readability, tiering

- [recommended] **Silhouette-first**: block strong silhouettes before detailing; the shape must be recognizable as a solid black spot, because players perceive spinning symbols at speed and peripherally. Similar silhouettes cause cognitive confusion [S1].
- [recommended] **Detail tiering**: low-pays = simple flat glyphs (stylized card ranks or simple themed tokens); premiums = layered detail + stronger rim light; WILD/SCATTER/BONUS visually distinct from the entire pay hierarchy (different framing device, e.g. banner/plaque/burst) [S1][S3].
- [observed] **Set size**: typical slot ships 9–14 unique reel symbols (commonly 4–5 lows, 3–4 premiums, wild, scatter, + feature specials), with idle / win / anticipation states per symbol [S1][S3]. Matches skill ids `L1..L5`, `H1..H4`, `WILD`, `SCATTER`, `FX*`.
- [observed] **Authoring size**: symbols authored at 256×256–512×512 px per state, transparent PNG, atlas-packed [S3]. On a 5×4 grid at 1080-wide portrait, on-screen cell size lands near 190–210 px CSS (~100–130 px physical at typical DPR scaling on small phones) — hence the working rule that a symbol must read at ~120 px [inferred from layout arithmetic; the "~120px readability" figure is a practitioner rule of thumb, not a published standard].
- [recommended] **Readability test gates**: (a) black-silhouette test; (b) 120 px downscale test on both the base background and each feature background; (c) motion-blur test (vertical blur approximating spin speed) — symbol class must still be guessable [S1][inferred: (c) is described qualitatively in sources as "readable during fast spins"].
- [recommended] **Negative space**: keep ~8–12% transparent margin inside the canvas so win-frame glows and squash-and-stretch don't clip [inferred from atlas-padding practice + symbol-state animation needs].

### 4. Prompt engineering for game assets (gpt-image / Midjourney v7 / SDXL / Flux)

#### 4.1 Cross-model consistency techniques

- [recommended] **Style anchor block**: a fixed, versioned paragraph (theme + material language + palette roles + lighting + rendering style) prepended verbatim to every prompt in the game. Studio pipelines are built around "curated prompt libraries, reference-first workflows" [S2].
- [recommended] **Palette lock**: name 4–6 exact colors (hex or precise names) with roles in every prompt; diffusion models follow named colors far better than vibes ("emerald green #1D7A46 accents, warm gold #D9A441 trim").
- [recommended] **Reference images over words**: image-to-image / reference conditioning beats textual description for consistency. Concretely: Midjourney `--oref` (V7 Omni-Reference, launched 2025-05-03) with `--ow` weight — `--ow 100` locks identity, drop below 100 when changing outfit/pose; only ONE oref image is accepted, so multi-character sheets must be composited into one reference [S7]. Midjourney `--sref` (Style Reference) carries the look; `--sv 6` is the current default style-reference model version, `--sv 4` was the pre-2025-06-16 V7 model; sref random/codes only work with `--sv 4`/`--sv 6` [S7]. Official docs deprecate `--cref` on V7 in favor of `--oref` [S7].
- [recommended] **Character/model sheets**: ask for "character model sheet, front view / side view / back view, T-pose" in ONE image — models understand the reference-sheet convention and keep the character consistent within a single generation; then crop [S6]. Same trick for symbol families: generate the whole low-pay set in one image for guaranteed mutual consistency, then slice [inferred extension of the same mechanism, widely practiced].
- [recommended] **Seed + settings capture**: record seed, model/version, sampler, steps, CFG for every accepted asset (feeds provenance §8 and enables re-rolls near an accepted look). Seed-locking + img2img is the lightweight alternative to LoRA training [S8].
- [observed] **Style LoRA** (SDXL/Flux): train on 15–40 images sharing one look for a project-wide style adapter; typical application strength 0.85–1.4. Licensing matters: FLUX.2-klein-base-4B is Apache-2.0 (outputs shippable, LoRAs distributable); FLUX.1-dev is non-commercial-gated [S8].
- [observed] **ControlNet for multi-view**: Flux + ControlNet + character LoRA workflows generate orthographic front/side/back sheets (e.g. 2048×1024, 20 steps, Euler, CFG 1, ≥12 GB VRAM); FLUX.2 Klein sprite-sheet LoRA emits a consistent 2×2 multi-view sheet in 4–6 steps on 8–12 GB GPUs [S8].
- [observed] **Multi-tool reality**: no single model dominates; a common stack is Midjourney for exploration, SDXL/Flux+LoRA for consistent batches, gpt-image for edits/transparency, Photoshop AI for cleanup [S2].

#### 4.2 Negative prompts — model-dependent

- [observed] **SDXL**: native CFG → negative prompts work; keep them SHORT (5–15 targeted terms). Long SD1.5-style negative walls degrade SDXL output. Add terms only for observed failures (extra fingers, watermark, text artifacts, frame/border) [S9].
- [observed] **Flux (dev/Klein)**: distilled models run CFG=1 where the negative prompt is ignored entirely; forcing CFG>~1.8 degrades quality. Workarounds (dynamic-CFG nodes, attention-space negative guidance like NAG/VSF) exist but cost quality/time [S9].
- [observed] **gpt-image / Midjourney**: gpt-image has no negative-prompt parameter — express exclusions as positive constraints in prose ("no text, no watermark, no border"); Midjourney has `--no` (weight −0.5 per term).
- [mandatory per skill contract] The skill's `art-prompts.json` must still carry a `negativePrompt` field for every asset (checklist line 1792); generators that lack the parameter fold it into prose. Encode per-backend adaptation rules, not one syntax.

#### 4.3 Transparency & sprite extraction

- [observed] **gpt-image API**: set `background: "transparent"` + `output_format: "png"`; mentioning transparency in the prompt also flips it on. Real-world success ~85–90% true-RGBA, so validate the alpha channel programmatically and retry/post-process failures [S6].
- [recommended] **Prompt reinforcement**: "isolated sprite, transparent background, RGBA PNG, crisp hard edges, no halos, no drop shadow, no glow" — models love feathered glows and those semi-transparent pixels break engine blending (fuzzy-blob particles in-engine) [S6].
- [mandatory per skill contract] **Magenta keying** (this skill's bundled `mcp__imagegen__*` tools): `transparent: true` renders on flat magenta for keying because the backing model cannot emit true alpha (CONVENTIONS §8). Keying pipeline: (1) chroma-key magenta with tolerance; (2) despill (desaturate magenta cast on edge pixels toward neighbor hue); (3) defringe 1–2 px; (4) alpha-threshold cleanup of isolated semi-transparent pixels. Magenta (255,0,255) is chosen because it is rare in natural art; the style bible must therefore ban magenta/hot-pink in sprite palettes [inferred: standard chroma-key logic applied to the documented magenta-key contract].
- [recommended] **Local matting fallback**: `rembg` (CLI/Python/server) for background removal; model choice matters (test several on representative assets), `-a` alpha-matting helps fuzzy edges but is slower; supports batch/watch-folder [S6].
- [recommended] **Halo/defringe pass** (always, regardless of extraction path): transparent PNG pixels retain RGB from the removed background; GPU blending bleeds it back as a halo. Fixes: premultiplied alpha in the engine, or a defringe pass that (a) zeroes/neighbor-fills RGB where alpha=0 and (b) decontaminates the 1–2 px semi-transparent rim (Photoshop Defringe 1–2 px, or scripted) [S6].

### 5. Blender 3D-to-2D pre-rendered pipeline

- [recommended] **Engine choice**: **Eevee** for stylized/NPR sprite renders — rasterized, GPU-fast, supports toon shading; sprite sheets multiply frames fast (states × directions × frames) so speed dominates. **Cycles** only when physically-accurate baked lighting IS the art direction (e.g. jewel/metal hero symbols with real caustic-ish speculars); shader nodes are largely shared so switching is cheap [S10].
- [recommended] **Use cases in a slot**: hero/premium symbols and coins (turntable spins), 3D reel-frame with real bevels, depth/parallax background layers, jackpot-wheel and coin-shower elements. 2.5D "rendered but stylized" is the dominant premium-slot look [S1][S3].
- [observed] **Turntable/sprite-sheet automation**: parent object to an empty acting as turntable, keyframe rotation, render N frames; established add-ons (Spritesheet Renderer — emits JSON frame metadata; Sprite Render Kit; DirectionalSpriteBatchRender for 1/8/16 directions) or a ~30-line bpy script + external montage (ImageMagick) [S10]. For slots, a 24–36-frame yaw turntable per premium symbol gives a smooth "coin spin" loop [inferred sizing: 10–15° steps, standard turntable practice].
- [mandatory per skill contract] **Headless automation**: `blender --background scene.blend --python script.py`; argument ORDER matters (script runs before the file loads if reversed); pass custom args after `--` and read `sys.argv[sys.argv.index("--")+1:]`. Works on CI/render nodes with no display [S11]. The skill must save every Blender action as a standalone `prompts/blender/*.py` runnable this way (CONVENTIONS §8).
- [recommended] **Render settings for sprites**: Film → Transparent for alpha; render PNG RGBA frames at 2× final size then downscale (cheap anti-aliasing); fixed camera (orthographic for symbols), fixed lighting rig shared across all symbol renders for lighting consistency [inferred: composite of documented practices — transparent film is the documented alpha path [S10][S15], supersampling and shared rigs are standard but rarely cited].
- [observed] **Emission/glow passes**: enable the Emission render pass and composite glow separately so the engine can pulse/tint it; emission behind glass/transmissive materials does not appear in the pass (by design — use Film→Transparent workarounds); separated passes are NOT auto-denoised (add Denoise nodes per pass); Cryptomatte is the modern way to mask per-object layers for animation-layer separation [S15].
- [observed] **Normal-map baking for lit 2D**: two routes. (a) From 3D: Cycles bake, tangent space (default; survives animation), Selected-to-Active for high→low poly; if lighting looks inverted in-engine flip the offending channel (swizzle). "Emission hack" bakes clean diffuse/color fast by routing color through an Emission shader and baking Emit [S15]. (b) From 2D art: SpriteIlluminator (CodeAndWeb) inflates a surface from sprite alpha and emits `<name>_n.png`, layout-matched by TexturePacker "pack with same layout"; free alternatives Laigter, Sprite DLight [S12].
- [observed] **Consuming normals in-engine**: PixiJS via `pixijs-userland/lights` (deferred shading: diffuse layer + normal layer + light layer render textures). Caveat for Spine: mesh deformation changes surface orientation but baked normal maps stay static — acceptable for subtle idle motion, wrong for large deformations [S12].
- [observed] **Sequenced Bake** (official Blender extension) batch-bakes material passes across animated frame ranges and assembles sprite sheets — useful for baked FX loops [S15].

### 6. Rigging: Spine skeletal vs sprite-sheet/cutout

- [observed] **Trade-off**: sprite sheets are free-form but every frame is stored (disk+RAM explodes with each animation; smoothness capped by frame count); Spine stores bone/animation data + one set of reused part images → smaller downloads, resolution-independent smoothness, runtime attachment swaps [S5].
- [observed] **Slot-specific Spine workflow** (Gamix Labs): one slot per symbol part for organized runtime swapping; bone groups per symbol column; spin loop as vertical bone motion; snap + attachment-swap at stop; squash-and-stretch bounce on land; draw-order layering puts glow/particle masks above symbols with zero extra frames; mesh deformation for flags/hair/liquid [S5].
- [observed] **Why iGaming standardized on Spine**: mobile-dominant play → file size and smooth 60fps matter; fast iteration without rebuilding art; runtimes for Pixi/Unity/custom casino engines [S5].
- [recommended] **Decision rule for the skill**: Spine (or equivalent cutout rig described in motion spec) for characters and premium-symbol win animations; sprite-sheet frames for stateless FX loops (explosions, coin bursts — 8–16 frames) where skeletal adds no value; simple transform/shader animation (scale, glow pulse, tint) in-engine for low-pay win states — cheapest of all [inferred synthesis of [S5] trade-offs].
- [recommended] **AI-art → rig prep**: flattened AI output must be segmented into parts and the occluded regions inpainted (gpt-image edit / SD inpainting) so parts can move without revealing holes; export layered PSD or per-part PNGs; keep pivot metadata [inferred: necessary consequence of cutout rigging on single-layer images; standard practice in cutout animation].

### 7. Atlasing, compression, export

#### 7.1 Packing

- [observed] **free-tex-packer / free-tex-packer-core** (MIT, npm): rotation, trim (`trimMode: trim|crop`, `alphaThreshold`), `detectIdentical`, `extrude`, MaxRects/OptimalPacker, Pixi exporter; core package scriptable in CI (`bun x`-able). GUI lacks CLI/multipack; core is the automation path [S12].
- [observed] **TexturePacker** (paid, CodeAndWeb): adds polygon trimming, multipack, 9-slice `defaultBorders` emission, KTX2/BasisU+ASTC export, Pixi cache-busting [S12].
- [recommended] **Settings**: `padding: 2` + `extrude: 1` minimum to stop bleeding under scaling/mipmapping; power-of-two, block-aligned (multiple-of-4) atlas dimensions — non-aligned KTX2 atlases throw GL_INVALID_OPERATION on some drivers; `allowRotation: true` (Pixi handles `rotate: 2` GroupD8), `detectIdentical: true` [S12][S14].
- [observed] **PixiJS consumption**: Spritesheet JSON drives `frame/orig/trim/rotate/uvs`; AssetPack's texturePacker pipe is the maintained build-time route for Pixi v8 [S12].
- [recommended] **Atlas partitioning for slots**: group by load phase — `preload` (loading screen + bare UI), `base` (symbols + reel frame + base bg), `feature`/`super_feature`/`ultimate_feature` (lazy-loaded per tier), `celebrations` (big-win) — so first-spin time isn't paying for feature art [inferred: standard streaming practice; aligns with skill's asset-manifest/device-profiles design].

#### 7.2 9-slice UI

- [observed] PixiJS `NineSliceSprite` takes `leftWidth/topHeight/rightWidth/bottomHeight` or falls back to `Texture.defaultBorders`; only TexturePacker (paid) emits defaultBorders in atlas JSON — with free-tex-packer, store slice insets in the skill's own asset-manifest and pass explicitly [S12]. [recommended] Author panels/buttons with ≥ slice-inset-sized uniform corners; corner ornament must live inside the fixed corner region.

#### 7.3 Compression & GPU formats

- [observed] **The VRAM argument**: PNG/JPG/WebP fully decode to raw RGBA on GPU — a 2048² texture is 16 MB VRAM regardless of file size. KTX2/Basis Universal transcodes to GPU-native (BC7 desktop / ASTC/ETC2 mobile) and stays compressed in VRAM: 4–8× texture-memory cut [S14].
- [observed] **Codec choice**: UASTC (≈BC7 quality; + Zstd supercompression; 1–2× JPEG size) for hero art, normal maps, UI; ETC1S (much smaller; global codebooks exploit cross-sprite correlation inside an atlas — good fit for symbol atlases) for bulk sprites [S14].
- [observed] **PixiJS v8**: built-in loaders — import `pixi.js/ktx2`, `pixi.js/basis`, `pixi.js/dds` before `Assets.load`; manifest lists variants `["bg.ktx2","bg.basis","bg.webp","bg.png"]` and Pixi picks the best supported; AssetPack auto-generates the variants at build time [S14].
- [recommended] **Decision rule**: symbols + UI atlases → KTX2 (ETC1S for lows/mid, UASTC for premium/hero + normal maps, sRGB on for color, off for normal/data maps); full-screen backgrounds/splash → WebP (or AVIF where supported) since they're single quads where download size dominates; ALWAYS ship PNG fallback via manifest variants [S14]. Keep PNG as the archival source of truth per CONVENTIONS §3 (`assets/art/`).
- [observed] **AVIF vs WebP**: AVIF compresses smaller at same quality but encodes slower and (like WebP) still decodes to raw RGBA in VRAM; both are download-size tools, not GPU-memory tools [S14].

#### 7.4 Upscaling & device profiles

- [observed] **Real-ESRGAN** (free, local, 2–4 GB VRAM): default 4× for AI-art assets; `--tile` to bound VRAM on big outputs; 4x-UltraSharp variant popular for AI art; judge results at intended display size, not 100% zoom. Local stack preferred over Topaz (subscription-only since Oct 2025) [S16].
- [recommended] **Generate-small → upscale → downscale chain**: generate at model-native res (1024²), Real-ESRGAN 4× when a hero asset needs >1024, then Lanczos-downscale to target — cleaner edges than direct large generation [inferred: widely-practiced pattern; individual steps documented in [S16]].
- [recommended] **Device profiles**: author @2x master (symbols 512², bg 3840×2160 or 2× canvas), emit @1x and @0.5x atlas variants; low-end profile = @0.5x + ETC1S + reduced FX frame counts. Matches "resolution sets defined during scoping per device" practice [S3].

### 8. Legal, provenance, disclosure (2024–2026)

- [mandatory — US law] **Copyrightability**: US Copyright Office *Copyright and AI, Part 2: Copyrightability* (2025-01-29): human authorship is bedrock; purely AI-generated output is NOT copyrightable; prompts alone (even complex, iterated ones) do not establish authorship; protection attaches where a human contributes perceptible authored expression, creative selection/arrangement, or modification of AI output — assessed case-by-case; no new legislation recommended [S17]. D.C. Circuit affirmed the human-authorship requirement in *Thaler v. Perlmutter* (March 2025) [S2].
- [mandatory — practical consequence] Raw AI symbol art a competitor could legally copy is a real commercial exposure for a slot studio. The pipeline should therefore route every shipped asset through documented human authorship steps (curation ≠ authorship; paintover, layered recomposition, palette rework, rig-driven modification DO count toward protectable contribution) and record them [S2][S17].
- [mandatory — contracts] **Contractor gap**: work-for-hire transfer clauses may transfer nothing if the deliverable was AI-generated (no copyright to transfer). Vendor agreements need explicit AI-use disclosure + warranty clauses [S2].
- [mandatory — EU, from 2026-08-02] EU AI Act Art. 50 requires machine-readable marking of AI-generated content (penalties up to €15 M or 3% global turnover); California SB 942 similar. C2PA Content Credentials (spec v2.2 May 2025, v2.3 Feb 2026) is the tamper-evident implementation layer; Adobe tools sign by default when enabled; CISA endorsed (Jan 2025). Known limit: platforms strip C2PA metadata on re-encode, so keep provenance server-side too [S18].
- [observed — platform norms] Steam (Jan 2024 policy, rewritten 2026-01-16): must disclose AI content players see/hear (art, audio, story, shipped code); behind-the-scenes efficiency tools exempt; disclosure shown publicly; ~20% of new releases carry the label. No equivalent mandatory regime yet on iGaming platforms or from gambling regulators — but Steam is the de-facto norm-setter and operators/aggregators increasingly ask in due-diligence questionnaires [S19][inferred final clause: due-diligence trend is reported anecdotally, not yet formalized].
- [observed — studio norms] Vendors gate AI use on explicit client approval and keep human-led pipelines available; recommended studio practice: adopt C2PA for origin metadata, keep an external disclosure policy for marketing assets, build provenance assurance into the pipeline rather than trusting AI detectors (no reliable detector exists; false positives common) [S2][S13].
- [mandatory per skill contract] **Provenance record per asset** (feeds `artifact-manifest.json`): assetId, generator tool + exact model/version, full prompt + negative prompt, seed/settings (steps, CFG, sampler, references used), timestamp, every post-process step (key/defringe/upscale/paintover) with tool + operator (human vs automated), human-authorship notes, license notes for any LoRA/base model (e.g. FLUX.1-dev non-commercial vs FLUX.2-klein Apache-2.0), final file hash [S2][S8][S17][S18].

### 9. Prohibited content (checklist lines 1804–1816)

[mandatory] Every prompt must exclude, and QA must check for: protected characters; protected logos; unlicensed celebrity likenesses (also implicates right-of-publicity + USCO Part 1 digital-replica report, July 2024 [S17]); direct copies of existing slot assets; "in the style of <living artist>" prompts (high legal/reputational risk; documented style-mimicry controversies) [S2][S17]; replication of another studio's visual identity (trade dress). Add: no magenta/hot-pink in sprite palettes (keying conflict, §4.3); no embedded readable text in generated images (AI text is unreliable — render text in-engine with real fonts) [S2, "AI-specific QA checks... text rendering"].

## Uncertainties & legal-review items

1. **"~120 px symbol readability" is a practitioner rule of thumb**, derived here from layout arithmetic — no standards body publishes a number. Encode as a testable gate (downscale test), not a cited standard. [inferred]
2. **No iGaming-regulator AI-art disclosure mandate found** (UKGC/MGA/Curaçao as of Aug 2026). Steam's regime is the de-facto norm; operator due-diligence questionnaires are anecdotal. Legal review should re-check per target jurisdiction at release time.
3. **Copyright of hybrid assets is case-by-case** — how much paintover/recomposition suffices for USCO registration is unsettled; the skill can only maximize and document human contribution, not guarantee protection. Needs counsel for any real-money release.
4. **Model/tool licensing drift**: FLUX.1-dev non-commercial vs FLUX.2-klein Apache-2.0 was true as of early 2026; gpt-image ToS grant commercial use of outputs but terms change. Provenance record must capture the license snapshot at generation time.
5. **Magenta-keying quality** for the bundled imagegen tools is a contract of this skill (CONVENTIONS §8) — success rates for clean keying are not independently benchmarked; the defringe/despill pass is mandatory insurance. [inferred]
6. **C2PA survivability**: metadata is stripped by most re-encoding platforms; treat embedded credentials as best-effort and the JSON provenance record as the authoritative store.
7. **KTX2 tooling variance**: block-alignment failures were reported on some ANGLE drivers; verify on real low-end Android before locking the compression matrix.
8. **EU AI Act Art. 50 applicability** to B2B slot assets (vs consumer-facing "deep fakes"/synthetic media) is debated; enforcement starts 2026-08-02 — flag for legal review rather than hard-coding behavior.

## Design implications for the Skill

**Style bible (templates/art-style-bible.md) must contain, in order:** theme statement (≤ 40 words, becomes the verbatim style anchor), narrative, mood board description, shape-language table (per symbol tier), material set (3–5 named materials), lighting spec (key direction + rim color, shared by ALL symbol prompts), camera spec (symbols: straight-on, no perspective; bg: stated horizon), palette table (4–6 hex colors × roles: bg-dominant / symbol-accent / ui-chrome / win-gold / tier accents), contrast rules, silhouette register (1-line black-shape description per symbol), character rules, environment rules, UI rules (incl. 9-slice insets), VFX rules (grayscale+tint policy), typography (display + UI face), per-tier visual escalation table (feature/super/ultimate), prohibited-references list, mobile-readability gates, accessibility gates.

**Symbol defaults:** 9–14 unique symbols (L1–L5 simple glyphs, H1–H4 detailed, WILD/SCATTER distinct framing devices); author at 512×512 RGBA PNG with 8–12% internal transparent margin; states: idle + win (+ anticipation for SCATTER); QA gates = black-silhouette test, 120 px downscale test on every background, alpha-integrity script check, halo check on light+dark backdrops at 200–400% zoom.

**Canvas/device defaults:** landscape master 1920×1080, portrait 1080×1920; backgrounds in ≥ 3 parallax layers + separate foreground overlays; device profiles hi (@1x, UASTC/WebP), mid (@1x ETC1S), low (@0.5x ETC1S, reduced FX frames).

**art-prompts.json schema (per prompt — mirrors checklist lines 1754–1802):** `assetId` (`img.*`), `category`, `purpose`, `subject`, `composition`, `cameraAngle`, `perspective`, `lighting`, `materials`, `paletteRole` (hex refs), `silhouetteRequirement`, `mobileReadability`, `negativeSpace`, `transparency` (`magenta-key | api-alpha | opaque`), `resolution`, `aspectRatio`, `animationLayers[]`, `consistencyRef` (style-anchor version + reference assetIds/seed), `negativePrompt`, `prohibitedContent[]`, `manualCleanup[]`, `exportFormat`, `fileName`, `provenance` (tool, model, seed, settings, timestamp, postProcess[], humanAuthorship, licenseNotes, sha256).

**Prompt construction rules:** every prompt = [style anchor block] + [asset-specific block] + [format block]; palette named as hex in-prompt; sprites: "isolated on flat magenta background, crisp hard edges, no drop shadow, no glow, no text, no watermark, no border"; consistent families generated as one multi-item sheet then sliced; premium/hero via reference-image conditioning (oref/img2img/LoRA) not prose; never rely on negative prompts on Flux-class backends (fold into positive constraints); no readable text in images — all text rendered in-engine.

**Asset list to prompt (checklist lines 1684–1752):** loading screen, splash, base bg (+ layers), foreground layers, reel frame, grid cells, low symbols, high symbols, wild, scatter, bonus, mystery, multiplier, collector, feature-exclusive symbols, 3 tier environments, feature HUDs, buttons, settings icons, spin-mode indicators, paytable elements, big-win typography (as art asset OR font+in-engine treatment — prefer the latter), particles, glows, trails, explosions, character parts, feature-buy UI, game icon, thumbnail, optional lobby art. Batch ALL compatible sprites into ONE `mcp__imagegen__generate_images` call per wave.

**Transparency pipeline (mandatory order):** generate (magenta key or API alpha) → chroma-key/verify alpha programmatically → despill → defringe 1–2 px (zero RGB where α=0) → alpha-threshold isolated semi-transparent pixels → QA on light+dark. Ban magenta/hot-pink from all sprite palettes.

**Blender scripts to always emit (`prompts/blender/*.py`, headless-runnable):** `turntable_symbol.py` (parametric: object path, 24–36 frames yaw, ortho cam, transparent film, 2× supersample, PNG frames + montage), `bake_normals.py` (tangent-space, selected-to-active, swizzle note), `emission_pass.py` (separate glow layer via Emission pass + per-pass denoise), `parallax_layers.py` (Cryptomatte/per-collection renders for bg depth layers). All accept args after `--`; document `blender --background file.blend --python script.py -- <args>`; warn on argument order.

**Rigging decision matrix:** characters + premium win anims → Spine-style cutout (motion spec lists parts, bones, pivot points; segmentation+inpainting step for AI art); FX loops → 8–16-frame sprite sheets; low-pay wins → in-engine transform/shader only. Normal maps optional "lit 2D" enhancement: `_n.png` suffix, same-layout packing, pixi deferred-lighting note; skip normals on heavily-deformed Spine meshes.

**Atlas/compression defaults:** free-tex-packer-core via bun script; padding 2, extrude 1, allowRotation+detectIdentical+trim on, POT block-aligned sizes ≤ 2048²; atlases partitioned preload/base/per-tier/celebrations; export matrix = KTX2 ETC1S (bulk sprites) / KTX2 UASTC+Zstd (hero, UI, normals) / WebP (fullscreen singles) / PNG (fallback + archival source); Pixi manifest variant arrays ktx2→basis→webp→png; 9-slice insets stored in asset-manifest (free packer doesn't emit them).

**Provenance (artifact-manifest.json):** one record per asset with the fields listed in §8; embed C2PA where tooling allows but treat the JSON record as authoritative; include model/LoRA license snapshot; record human post-work explicitly to support copyrightability; never claim copyright registration — flag "human-authorship documentation available" only.

**Hard prohibitions (encode in every prompt's `prohibitedContent` + QA):** protected characters/logos, celebrity likenesses, copies of existing slot assets, living-artist style imitation, other studios' trade dress, readable in-image text, magenta in sprite art, photorealistic depictions of real people, and any watermark-like artifacts.
