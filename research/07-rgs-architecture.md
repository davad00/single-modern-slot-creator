## Findings

### 1. Server-authoritative outcome generation

- **[mandatory, all regulated jurisdictions]** All outcome-determining computation (RNG
  draw, reel-stop selection, win evaluation, feature awards, multipliers) executes on the
  server (RGS); the client is a display layer that sends requests and renders results. This
  is both the certification model (GLI-19 v3.0 Ch. 3 RNG requirements + Ch. 4 game
  requirements are evaluated against the server system, not the client) and the universal
  industry architecture [S11][S13].
- **[mandatory, UKGC]** RTS 7 governs generation of random outcomes; RTS 7E additionally
  requires the system to "clearly and accurately display the result of the game or event
  and the customer's gamble" for a length of time sufficient to understand it [S10].
- **[observed, Stake Engine]** A fully *precomputed* variant of server-authority exists and
  is production-proven: games uploaded to Stake Engine "must consist of static files" —
  every possible outcome is pregenerated by the Python math-SDK into compressed game files;
  at bet time the RGS samples a simulation number proportional to its weight and returns
  the corresponding event list through the `/play` API response [S5][S2]. Live (per-spin
  computed) RGSs are the other major pattern; both are server-authoritative [S13].
- **[mandatory, certification]** GLI-19 v3.0 §2.3.2: critical control program components
  must be verified as authentic using a cryptographic hash (message digest ≥ 128 bits) at
  minimum once every 24 hours (self-authentication of deployed game/system software) [S11][S16].
- **[recommended]** Verifiable-fairness overlays (provably-fair seeds, VRFs) are growing in
  crypto-adjacent markets but are additive; they do not replace certified-RNG,
  server-authoritative outcome generation in regulated markets [S13].

### 2. Client presentation boundaries

- **[observed, Stake Engine]** The entire client-visible round is an ordered list of
  `events`; the math-SDK docs state "Anything not contained within or implied by the events
  cannot be shown to the player." Each event is `{ "index": int, "type": str, ...fields }`,
  emitted as a snapshot immediately after each board transformation (deal, tumble, counter
  update), and the frontend replays them in `index` order [S4].
- **[mandatory, UKGC]** The gambling system "must not celebrate a return which is less than
  or equal to the total stake gambled" (no win-line fanfare for losses-disguised-as-wins);
  result display duration must be reasonably sufficient (RTS 7E + 2021 game-design rules)
  [S10].
- **[mandatory, UKGC]** RTS 2: amount being gambled (incl. currency conversion) must be
  displayed before commitment; all gaming sessions must display net position (total
  winnings minus total losses since session start) [S10].
- **[inferred]** Corollary used by every event-manifest platform: presentation speed
  controls (turbo/skip) may only change *when* events render, never *what* they encode —
  because settlement values live in the server manifest, the final balance is identical in
  every presentation mode. Direct consequence of the "client renders events" model in [S4];
  not stated verbatim in any single fetched source.

### 3. Round lifecycle & round IDs

- **[observed, Stake Engine]** Lifecycle: `POST /wallet/authenticate` (sessionID →
  balance, bet config, and the player's current-or-last `round`) → play request
  (`{amount, sessionID, mode}`; debits balance, creates round) → optional
  `POST /bet/event` progress checkpoints → `POST /wallet/end-round` (credits any win,
  closes round). If `/wallet/authenticate` returns an *active* round, "frontends should
  continue the round" [S1]. `/end-round` must be called explicitly when the win > 0; the
  math config's BetMode `auto_close` flag can let the RGS close zero-interaction rounds
  automatically [S1][S5].
- **[observed, Hub88]** The `round` field "is used to relate all bets and wins made in one
  round. All transactions related to the same round have the same value... The ID is not
  unique through the whole system" (uniqueness is derived from game + user + round);
  `round_closed` (nullable boolean) marks closure [S6].
- **[recommended]** Two distinct ID levels are therefore needed: a **round ID** (groups all
  money movements of one game round) and per-movement **transaction IDs** (globally unique,
  idempotency scope). Aggregators additionally carry a `request_uuid` per HTTP call that
  the receiving side must echo back verbatim for log correlation [S6][S7].
- **[observed, Hub88]** One round can contain multiple debits and credits (e.g., feature
  buys, aggregated freespin settlements via `is_aggregated: true` merging e.g. 10 freespin
  wins into one credit) [S6].

### 4. Idempotency

- **[mandatory, aggregator contract]** Every money endpoint is keyed by a unique
  transaction ID (`transaction_uuid` at Hub88). "Before any balance change on bet or win,
  the Operator must verify the transaction_uuid hasn't already been processed"; a true
  duplicate (same uuid, same content) must be answered with the *original successful
  result*, not an error; the same uuid with *different* content (different reference tx,
  amount, currency, round, user or game) is the error case
  (`RS_ERROR_DUPLICATE_TRANSACTION`) [S6][S7].
- **[recommended]** CasinoWebScripts wallet docs state the same rule from the RGS side:
  "if you processed a transaction in the past, do not process it again, and do not reject
  duplicate transactions silently — always reply with a success status if already handled";
  they also recommend storing zero-amount transactions (for idempotency and progress
  tracking) without touching the balance, and rejecting requests older than a timestamp
  window (~15 minutes) [S12].
- **[observed, Hub88]** Retry policy that idempotency must survive: bet calls are retried
  3× with 1 s timeout on transport failure; a failed bet then generates a rollback retried
  up to **500 times with exponential backoff**; win deliveries may be retried indefinitely
  depending on the supplier RGS [S6].
- **[mandatory]** `transaction_uuid` values must be stored on both sides ≥ 4 months for
  reconciliation (Hub88 contract) [S6]; GLI-19 requires audit-grade retention of gameplay
  records generally (Ch. 2 + appendices) [S11].

### 5. Rollback / cancel semantics

- **[mandatory, aggregator contract]** Rollback is a first-class message:
  `POST /transaction/rollback` carries its own `transaction_uuid` plus
  `reference_transaction_uuid` = the uuid of the transaction to undo. The operator locates
  the referenced transaction, reverses its effect, returns the new balance [S6].
- **[mandatory, Hub88]** Token/session validity must NOT be enforced for wins and
  rollbacks — they may legitimately arrive after the session died [S7]. There is a
  dedicated status for "win references a bet we never saw / already rolled back"
  (`RS_ERROR_TRANSACTION_DOES_NOT_EXIST`) [S6][S7].
- **[observed, CasinoWebScripts]** Alternate cancel convention: `cancelbet` /`cancelwin`
  messages whose txid references the original via prefix (`cancel_<original-txid>`) and
  whose amount is the negation of the original; duplicates of a cancel are also answered
  with success + current balance [S12].
- **[inferred]** A rollback of a *not-yet-seen* transaction must be remembered ("rollback
  tombstone") so a late-arriving original bet is refused; this is the standard resolution
  of the rollback/bet race implied by Hub88's duplicate + does-not-exist statuses and their
  500-retry rollback policy, but no fetched page states the tombstone rule verbatim.

### 6. Outcome signatures & transport authentication

- **[observed, Hub88]** All wallet-API request bodies are signed with **RSA-SHA256** over
  the exact raw bytes, base64-encoded into the `X-Hub88-Signature` header; each party
  verifies with the other's public key (2048-bit keys generated via
  `openssl genrsa 2048`). Verification must run against the raw body "without any
  deserialization" — canonicalization bugs are the #1 integration failure
  (`RS_ERROR_INVALID_SIGNATURE`) [S6][S8].
- **[observed, Stake Engine]** Client↔RGS integrity is instead achieved by hashing: on
  game upload the RGS extracts and hashes `payoutMultiplier` values to ensure the CSV
  lookup table and the compressed logic file are identical; sessions are authenticated by
  `sessionID` on every call [S1][S2].
- **[recommended]** Detached signature over the outcome manifest (JWS or HMAC in dev)
  gives the client/support tooling a verifiable artifact per round; production-grade
  request signing between RGS and wallet is the industry norm (TLS + request signing + IP
  allowlisting on wallet callbacks) [S6][S8][S12].

### 7. Configuration hashes & math-version references

- **[mandatory, certification]** GLI-19 v3.0 §2.3.2 (≥128-bit digest, ≤24 h cycle) applies
  to critical control program components — in practice the certified artifact set (game
  logic, RNG, paytables/config) must be hash-verifiable so the lab-certified build can be
  matched to the deployed build [S11][S16].
- **[observed, Stake Engine]** The publish bundle is content-addressed by construction:
  `index.json` (modes: `name`, `cost`, `events` file, `weights` file) + per-mode
  `lookUpTable_<mode>_<n>.csv` (uint64 columns: simulation number, weight, payout
  multiplier) + `books_<mode>.jsonl.zst` (one JSON round per line: `id`, `events[]`,
  `payoutMultiplier` as integer ×100 of bet, e.g. 1150 = 11.5x). The RGS validates format
  and payout-hash equality on upload; games are then served from an immutable versioned CDN
  path `.../{GameID}/{GameVersion}/index.html` [S1][S2].
- **[recommended]** Every round record should reference the exact math version + config
  hash active when it was played, so replays/disputes resolve against the right artifacts;
  versioned CDN paths and upload-time hashing at Stake Engine are the observed mechanism
  [S1][S2]; GLI-19 record-keeping expectations are the regulatory driver [S11].

### 8. Outcome replay & game history

- **[mandatory, UKGC]** RTS 1B: customers must have easy access to ≥ 3 months of account
  and gambling history without contacting the licensee, and ≥ 12 months on request. History
  must include bets placed, results of bets, winnings paid; where detailed game info is not
  directly available, at minimum the last game played must be easily accessible [S10].
- **[mandatory, aggregator contract]** Hub88's Transactions API exposes every gameplay
  transaction with status + unique IDs, filterable by time window or by round (at least one
  filter required) — operators are expected to reconcile and to investigate disputes from
  it; `supplier_transaction_id` exists specifically "for support investigations" [S6][S7].
- **[recommended]** Round replay = re-rendering the stored outcome manifest/event list for
  a given round ID. In the precomputed model this is trivial (book id → events); patent and
  vendor literature describes storing critical session data keyed by a reconnect/round
  identity code for exact reconstruction [S4][S17][S13].

### 9. Interruption recovery & completion-on-next-launch

- **[mandatory, UKGC]** RTS 10A/10B: if interruption occurs *after* the gamble is received
  and the customer has no further influence, the result stands; if *before* an outcome was
  generated, the stake is returned; for stateful/multi-stage games "all reasonable steps
  should be taken to restore the game to its last known state to enable the customer to
  complete the game"; systems must be able to void gambles and must retain sufficient
  information to restore pre-failure state (explicitly including counters like tokens
  collected); progressive jackpot values restored to pre-failure state [S9].
- **[mandatory, GLI-19]** An incomplete game must be resolved before the player may start
  another instance of the same game; the platform must keep records enabling recovery of
  incomplete games; a player device unresponsive for **30 minutes** must cause session
  termination; if full recovery is impossible the system must void bets and pays and
  return or forfeit wagers as appropriate (v2.0 §2.7.2, carried into v3.0 Ch. 4) [S11].
- **[mandatory, Indiana 68 IAC 25-10-4, representative US rule]** Single-stage games: the
  system must ensure the patron can view the outcome after interruption; multi-stage games:
  all incomplete transactions must provide a method for the patron to complete the game if
  further input is required [S17].
- **[observed, Stake Engine]** Concrete completion-on-next-launch mechanism:
  `/wallet/authenticate` returns the active round; the frontend must detect it and resume
  (seek presentation to the recorded `/bet/event` checkpoint, then `/end-round`). The
  docs warn that once a round is closed it cannot be resumed — hence bonus/multi-step modes
  keep `auto_close = false` [S1][S5].
- **[observed, operator T&Cs]** Unresolved bets/incomplete rounds commonly stay active
  until re-opened and are voided/forfeited after 60 days (operator-side clause, varies)
  [S9-adjacent, lawinsider clause samples; treat as market practice, not regulation].

### 10. Feature-state persistence

- **[mandatory, UKGC/GLI]** The recovery duties above extend to *feature* state:
  "the state of a deck of cards, any hands dealt, and the number of tokens collected"
  (RTS 10B guidance) — i.e., mid-feature counters, remaining free spins, accumulated
  multipliers, and collection meters must be durably stored server-side [S9][S11].
- **[observed, Stake Engine]** `POST /bet/event` exists precisely to checkpoint
  in-progress presentation state ("records in-progress actions so gameplay can resume
  after a disconnect"); the server already knows the full outcome, so the checkpoint is a
  *presentation resume pointer*, not new entropy [S1].
- **[inferred]** In precomputed-manifest systems, persistent multi-round feature state
  (e.g., a collection meter spanning rounds) must either be encoded in the math model as
  part of each round's outcome or handled by a stateful RGS extension; Stake Engine's
  static-file model implies per-round independence (each book line is a complete round),
  so cross-round persistent meters are out of scope there.

### 11. Maximum-win termination

- **[observed, Stake Engine]** BetMode carries a maximum win amount; win distributions are
  optimized against it; the payout hash check enforces that no book exceeds declared
  values [S5][S2].
- **[recommended]** When cumulative round win hits the cap mid-feature, the server ends
  the round immediately (remaining free spins/cascades void), pays exactly the cap, and
  the manifest encodes an explicit terminal step so the client can present it. This is
  standard published game-rules behaviour across modern studios ("wins beyond max win are
  capped; round ends") — market-rule observation; no single fetched primary page states
  it, hence [recommended] backed by the no-unbounded-liability certification principle in
  [S11].

### 12. Wallet integration boundary (seamless wallet pattern)

- **[observed, industry-wide]** Two models: **seamless/single wallet** (operator holds the
  only balance; RGS/aggregator makes synchronous debit/credit callbacks per round) and
  **transfer wallet** (funds moved into a provider-held balance). Seamless is the modern
  default; Hub88 offers both [S6][S7][S18].
- **[mandatory, contract shape]** The canonical operator-implemented callback set (Hub88
  names): `/user/info`, `/user/balance`, `/transaction/bet` (debit), `/transaction/win`
  (credit, requires `reference_transaction_uuid` of the bet), `/transaction/rollback`.
  Shared response: `{user, status, request_uuid, balance}`. The RGS **never** computes the
  balance; it displays what the wallet returns [S6].
- **[observed]** Money units differ per platform and must be integer: Hub88 = value ×
  100,000 int64 ($3.56 → 356000); Stake Engine = micro-units, 6 decimal places
  ($1 → 1,000,000), currency affects display only [S1][S6]. Non-integer/binary-float money
  is never used on the wire.
- **[observed, Hub88]** Status vocabulary the game server must map:
  `RS_OK`, `RS_ERROR_UNKNOWN`, `RS_ERROR_INVALID_PARTNER`, `RS_ERROR_INVALID_TOKEN`,
  `RS_ERROR_WRONG_CURRENCY`, `RS_ERROR_NOT_ENOUGH_MONEY`, `RS_ERROR_USER_DISABLED`,
  `RS_ERROR_INVALID_SIGNATURE`, `RS_ERROR_TOKEN_EXPIRED`, `RS_ERROR_WRONG_SYNTAX`,
  `RS_ERROR_WRONG_TYPES`, `RS_ERROR_DUPLICATE_TRANSACTION`,
  `RS_ERROR_TRANSACTION_DOES_NOT_EXIST`, `RS_ERROR_LIMIT_REACHED` [S6].
- **[mandatory, flow]** Debit precedes outcome presentation: bet is debited when the round
  starts; a failed/timeout debit means no round (and triggers rollback of any partial
  state). Win is credited at settlement (`/end-round` at Stake Engine; `/transaction/win`
  through an aggregator) [S1][S6].

### 13. Error handling

- **[observed, Stake Engine]** Client-facing RGS error codes: 400-class `ERR_VAL` (invalid
  request), `ERR_IPB` (insufficient balance), `ERR_IS` (invalid session/timeout),
  `ERR_ATE` (auth/token expired), `ERR_GLE` (gambling limits exceeded), `ERR_LOC` (invalid
  location); 500-class `ERR_GEN`, `ERR_MAINTENANCE` [S1].
- **[mandatory, UKGC]** RTS 10B: capability to void gambles (with or without manual
  intervention) and suspend play on failure; policies must not systematically disadvantage
  customers [S9].
- **[recommended]** Distinguish three client error classes with distinct UX: (a)
  recoverable transport errors → silent retry then `reconnecting` state; (b) round-state
  conflicts → force refetch of authoritative round and resume; (c) terminal
  (session/location/limits) → block play, show message, offer lobby exit. Grounded in the
  error vocabularies of [S1][S6] mapped onto the RTS 10 fairness duties [S9].
- **[observed, Hub88]** Bet validation errors on `/play`-equivalents include divisibility
  and range rules: Stake Engine bets must be within `minBet`..`maxBet` and divisible by
  `stepBet`, with recommended `betLevels` presets [S1].

### 14. Audit event hooks

- **[mandatory, GLI-19]** The platform must log significant events for audit: gameplay
  transactions with IDs and status, incomplete-game records, critical-file verification
  results, firewall/config changes (Appendix B: all firewall configuration changes and
  connection attempts logged; periodic security testing; PII-handling assessment) [S11][S16].
- **[mandatory, contract]** Every wallet call carries `request_uuid` echoed both ways for
  cross-party log correlation; both parties retain transaction records ≥ 4 months (Hub88)
  [S6]. UKGC RTS 1 forces 3–12 month player-visible history on top [S10].
- **[recommended]** Emit structured audit events at minimum on: round_open (bet debited),
  outcome_committed, each wallet call+result, settlement, rollback, recovery-resume,
  max-win termination, void. Immutable append-only storage; monitoring for settlement
  drift, rollback spikes, error anomalies [S12][S6][S11].

### 15. Deterministic development-mode outcome generation & QA forcing

- **[observed, Stake Engine]** The math-SDK ships a first-class QA forcing mechanism:
  during simulation each notable occurrence is recorded via `self.record({...})` →
  `force_record_<betmode>.json` entries of shape
  `{"search": {"gametype": "basegame", "kind": 5, "symbol": "scatter"}, "timesTriggered": 22134, "bookIds": [7, 12, ...]}`
  plus a merged `force.json` listing every search key — intended so "a drop-down menu, or
  something of the sort can be created" for prototyping, i.e. pick a criterion → replay a
  known book ID deterministically. Keys unique; a book ID may appear under multiple keys;
  entries are only imprinted after a simulation is accepted [S3].
- **[observed, Stake Engine]** Deterministic replay is inherent to the precomputed model:
  book `id` → exact event list → exact presentation; dev tooling only needs to select the
  id instead of sampling by weight [S2][S3].
- **[recommended]** Dev-mode providers should be (a) seeded PRNG-driven so any round is
  reproducible from its seed, and (b) scenario-forcing (force feature trigger, force
  max win, force specific grid) via force-file-style indices. **Never in production
  builds:** the certified system's outcomes must come only from the certified RNG path
  (GLI-19 Ch. 3), so cheat/force tooling must be compile-time excluded or server-rejected
  outside dev environments [S11][S3]. [inferred: the exclusion mechanism itself; no source
  documents how studios strip force tools from prod, because prod force tools would fail
  certification by definition.]

### 16. Outcome-manifest design: precomputed full-round vs stepwise

- **[observed, Stake Engine — precomputed full-round]** The entire round (base result +
  all cascades + all feature spins) is one book line: `{"id", "events": [...],
  "payoutMultiplier"}`. Cascades/tumbles are encoded as consecutive snapshot events (board
  state after each removal/refill), free-spin counters as counter-update events. The client
  receives everything at once and replays; `/bet/event` checkpoints how far presentation
  got [S2][S4][S1].
- **[observed, stepwise/live RGS]** Other RGSs compute per step and push results over
  WebSocket/HTTP per interaction; the round stays open across multiple wallet transactions
  sharing one `round` id (Hub88's model explicitly supports many transactions per round)
  [S6][S13].
- **[recommended]** For a single-slot skill: precomputed-full-round manifests are strictly
  simpler and safer (single settlement, trivial replay/recovery, presentation-mode
  equivalence testable by construction) unless a mechanic requires mid-round player
  decisions (gamble/pick with real agency), which forces stepwise. Player *pick* features
  with predetermined results can remain precomputed [inferred from S2/S4 event model +
  RTS 10 stateful-game duties].

   revision date (post-2021 game-design update, any 2024–2026 amendments) was not pinned;
   legal review should confirm the current RTS edition and any new interruption/history

   v2.0; v3.0 restructured chapters and the exact v3.0 numbering was not verified page-by-
   page (PDF not parsed in full). Verify against the official PDF before citing sections in
   compliance docs.
3. **Private aggregator specs.** EveryMatrix/SOFTSWISS/Relax/Slotmill/Swintt seamless-wallet
   specs are non-public; the "common contract shape" here is generalized from Hub88 +
   CasinoWebScripts + industry summaries. A real integration must be built against the
   target aggregator's NDA'd spec.
4. **Rollback tombstone rule** (§5 [inferred]) and **prod-exclusion mechanism for force
   tools** (§15 [inferred]) are best-practice inferences; no public primary source states
   them verbatim.
5. **60-day void window** for unresolved rounds is an operator-T&C sample, not a
   regulatory constant; jurisdictions differ.
6. **Jurisdiction variance** on completion-on-next-launch: UKGC prefers restore-and-
   complete; some US states additionally require the patron to *view* the outcome; some
   markets permit auto-settlement server-side. The skill's default (auto-complete
   server-side at expiry, restore-on-launch otherwise) needs per-market legal sign-off.
7. **Stake Engine terms**: engine.stake.com targets Stake.com distribution (crypto/social
   models, XGC/XSC currencies); using its SDK conventions as a design reference is fine,
   but its jurisdictional acceptability is a separate legal question.

## Design implications for the Skill

Rules the slot-creation skill should encode (aligned with CONVENTIONS.md §4.4, §5, §7):

### Contract & lifecycle
1. **Two-provider abstraction**: `OutcomeProvider` interface with exactly two
   implementations — `DevRoundProvider` (deterministic, seeded xoshiro128**, scenario
   forcing) and `RgsAdapter` (HTTP, production). The client imports only the interface;
   the dev provider is tree-shaken/flag-gated out of production builds and the RGS adapter
   refuses non-HTTPS or dev-flagged hosts in prod mode.
2. **Round lifecycle endpoints** (RGS adapter surface, modeled on S1/S6):
   `authenticate(sessionId) → {balanceMinor, config, activeRound?}`,
   `play({betMinor, mode, roundSeq}) → {round, balanceMinor}`,
   `event({roundId, resumePointer})` (presentation checkpoint),
   `endRound(roundId) → {balanceMinor}`. If `authenticate` returns an active round the
   client MUST enter `recovering` and resume before allowing new bets (GLI-19: incomplete
   game resolved before a new instance).
3. **IDs**: `roundId` `^rnd_[A-Za-z0-9_-]{6,}$` (server-issued); every wallet-affecting
   call carries a client-generated UUIDv4 `transactionId` (idempotency key) plus echoes a
   per-request `requestId`. Win/settlement messages carry `referenceTransactionId` of the
   originating bet. All three appear in the outcome manifest header.
4. **Money**: integer minor units end-to-end (`*Minor` fields, CONVENTIONS §5). Document
   the unit-scale conversion explicitly in the adapter (Hub88 ×100,000; Stake ×1,000,000;
   ours = minor units) — unit-scale mismatch is a classic integration bug.
5. **Bet validation** client-side mirror: `minBet ≤ bet ≤ maxBet`, `bet % stepBet == 0`,
   prefer server-provided `betLevels[]`; server remains authoritative and returns
   `ERR_VAL`-class errors otherwise.

### Idempotency & rollback
6. Duplicate delivery of any money message returns the original result with success
   status — never a second application, never a silent rejection. Same-ID-different-
   content returns `DUPLICATE_TRANSACTION` error. Store zero-amount transactions too.
7. Rollback handler: reverse by `referenceTransactionId`; if the referenced transaction
   was never seen, record a tombstone and refuse a later-arriving original. Design for
   aggressive retry storms (Hub88: 3× bet retries; up to 500 rollback retries with
   exponential backoff) — handlers must be O(1)-idempotent under repetition.
8. Session-token rules: wins and rollbacks must be accepted after session expiry; only
   bets require a live token.

### Outcome manifest (per CONVENTIONS §7, confirmed by research)
9. Precomputed full-round manifest is the default: ordered `steps[]`, each a snapshot
   after one board transformation (matches Stake Engine's event-snapshot pattern), with
   `stepId`, `type`, `grid`, `wins[]`, `scatterCount`, `multiplier`, `events[]`. Header
   fields: `roundId`, `betMinor`, `totalWinMinor`, `payoutMultiplierX100`, `gameVersion`,
   `mathVersion`, `configHash`, `rngInfo` (dev: seed + provider id; prod: RGS reference),
   `signature` (detached JWS/HMAC over manifest-minus-signature; HMAC placeholder in dev).
10. Equivalence invariant as an automated test: for any manifest, presentation in
    normal/quick/turbo/skip modes yields byte-identical settlement (final balance, win).
    This is testable precisely because the manifest is complete before presentation starts.
11. Max-win termination is an explicit manifest step (`max_win_termination`) that (a)
    truncates all subsequent steps, (b) sets `totalWinMinor` exactly to cap, (c) carries a
    presentation event `anim.maxwin.reached`. Simulator must prove no book exceeds the cap
    (Stake Engine enforces this by hashing payout columns — mirror with a validation gate).

### Recovery & replay
12. Recovery = re-fetch committed manifest + `resumePointer` (last acknowledged stepId
    from `event()` checkpoints), seek presentation instantly to that step, then continue.
    Never re-randomize; never re-debit. On `authenticate` with active round →
    `recovering` state (CONVENTIONS §4.4 state machine).
13. Persist server-side per round: manifest, resumePointer, wallet transaction log,
    feature counters (free spins remaining, accumulated multiplier, collection meters) —
    RTS 10B names counters explicitly. Client-side persistence is a cache only.
14. Encode a `voidRound` path: if recovery is impossible, void and return the stake
    (RTS 10B / GLI-19); write the void as an audit event and a terminal manifest step.
15. Replay/history: expose `getRoundHistory(limit, cursor)` and `getRound(roundId) →
    manifest` in the adapter interface; generated game ships a history UI stub showing at
    least the last round in full detail (RTS 1 minimum), with the manifest as the data
    source so replay is exact re-presentation.
16. Idle timeout default: terminate/park the session after 30 minutes of unresponsiveness
    (GLI-19); unresolved rounds auto-resolve server-side per jurisdiction policy
    (configurable; default: complete with stored outcome and credit wins).

### Dev-mode determinism & QA forcing
17. Dev provider must support: (a) `seed` param → fully reproducible round streams;
    (b) `force` param accepting force-file-style criteria
    (`{"kind": 3, "symbol": "SCATTER"}` → feature trigger; `super_feature`,
    `ultimate_feature`, `max_win`, `dead_spin`, specific `bookId`); (c) generation of
    `force_record_<mode>.json` + merged `force.json` from the simulator so QA UIs can
    build dropdowns of forceable scenarios (Stake Engine pattern, S3).
18. Force/cheat surface is compiled out of production bundles (`import.meta.env`-gated,
    verified by a build assertion that the prod bundle contains no force symbols) and the
    dev provider throws if `NODE_ENV=production`-equivalent. Validation report must include
    this check.

### Signatures, hashes, versions
19. `configHash` = `sha256:` over canonical JSON of all `config/*.json` (CONVENTIONS §5);
    embed in manifest header, boot log, and simulation reports. Simulator refuses to run
    if hash of loaded configs ≠ hash recorded in the report being extended.
20. Dev outcome signature: HMAC-SHA256 with a documented dev key + a `signatureScheme`
    field so production can swap to detached JWS (RS256/EdDSA) without schema change.
    Wallet-boundary signing (RSA-SHA256 over raw body, base64 header, à la
    `X-Hub88-Signature`) is documented in the integration guide as the aggregator-side
    expectation, with the raw-bytes-no-reserialization warning called out.
21. Every simulation report + manifest carries `gameVersion`, `mathVersion`,
    `configHash`; the generated client displays them in a debug/about panel for
    lab/support correlation.

### Wallet boundary
22. The generated game NEVER computes balance. It renders `balanceAfterMinor` returned by
    the wallet/RGS; optimistic UI is allowed only between `play` request and response,
    reconciled on every response. Debit-at-bet, credit-at-settlement; one settlement per
    round in the default (precomputed) model; `roundClosed` flag on the final transaction.
23. Error-code map in the adapter: normalize vendor codes into
    `{INVALID_SESSION, AUTH_EXPIRED, INSUFFICIENT_FUNDS, LIMITS_EXCEEDED,
    INVALID_LOCATION, VALIDATION, DUPLICATE, UNKNOWN_TRANSACTION, MAINTENANCE, GENERAL}`
    with the three UX classes: retry-silently / refetch-round / terminal-block.
24. Audit hooks: structured events (`audit.round_open`, `audit.outcome_committed`,
    `audit.wallet_call`, `audit.settlement`, `audit.rollback`, `audit.recovery`,
    `audit.void`, `audit.maxwin`) emitted through a pluggable sink; default sink =
    append-only JSONL in dev. Retain transaction records ≥ 4 months in any real
    deployment guidance doc.

### Scope guardrail
25. The skill generates the *game-side* contracts only: the OutcomeProvider interface, dev
    provider, RGS adapter skeleton with typed request/response models, manifest schema, and
    an integration guide mapping our contract onto the seamless-wallet callback pattern.
    It does NOT generate operator wallets, aggregator middleware, or player account systems
    (per prompt.txt line 1558 and CONVENTIONS §1).
